博客的 GitHub Pages 部署

Mozaitii / 2026-07-28

本博客部署在 GitHub Pages 上，域名 mozaitii.github.io。从写完一篇草稿到它在网上可访问，中间只隔了一次 git push——剩下全交给 GitHub Actions 流水线，这篇把整套部署方案拆开讲讲。

整体架构：两个仓库

关键在于它其实是两个 GitHub 仓库，分工完全不同：

仓库内容作用
moz_blog_sourceHugo 源码：content/、layouts/、static/、主题子模块唯一手动维护的地方
mozaitii.github.io编译好的静态站（HTML/CSS/图片）GitHub Pages 直接托管它

链路是这样的：

写博客 → 源码仓库 moz_blog_source
              │  git push main
              ▼
       GitHub Actions 流水线（编译 Hugo）
              │  推送构建产物
              ▼
       发布仓库 mozaitii.github.io（main 分支）
              │  GitHub Pages 托管
              ▼
          https://mozaitii.github.io/

注意一个细节：docs/（hugo 的构建输出目录）在源码仓库里是被 .gitignore 忽略的，publishDir 也指向它，也就是说源码仓库里只有「配方」，没有「成品」——成品由 CI 每次从源码现编出来。

为什么不用「单仓库 + docs/ 目录」发布

GitHub Pages 有一个更常见的玩法：单个仓库里把 hugo 产物放到 docs/ 目录，然后在仓库的 Settings → Pages 里选「Deploy from a branch → docs/」，这样只有一个仓库、不需要额外仓库和 token。

刚开始也这么考虑过，最后还是选了独立发布仓库，原因是：

  • 源码和产物不混在同一个历史里。单仓库意味着每次提交都带着编译产物，历史里全是 docs/ 的噪音提交；产物和源码解耦后，main 分支就是干净的内容变更。
  • CI 每次全量重编，产物可复现。本地 hugo 产生的中间文件（比如 Hugo 图片处理缓存的 resources/）不会误入库。
  • 发布仓库本身也是一个通用的「静态托管位」,将来如果想挂别的静态站、甚至多语言分站，可以独立控制。

代价是要维护一个 PAT（见下文），以及在 .github/workflows/ 里多写一个文件。对「免费 + 自动」来说这笔账很划算。

Workflows工作流

部署的全部魔法都在 .github/workflows/deploy.yml 这一个文件里：

name: Deploy Hugo Site to GitHub Pages

on:
  push:
    branches: [main]   # 推到 main 就触发
  workflow_dispatch:   # 也支持在 Actions 页面手动触发

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          submodules: true        # ← 关键：拉取主题子模块

      - name: Setup Hugo
        uses: peaceiris/actions-hugo@v2
        with:
          hugo-version: 'latest'

      - name: Build
        run: hugo --minify        # 构建产物输出到 docs/（publishDir）

      - name: Deploy to mozaitii.github.io
        uses: peaceiris/actions-gh-pages@v3
        with:
          personal_token: ${{ secrets.GH_PAT }}      # 见下节
          external_repository: mozaitii/mozaitii.github.io
          publish_dir: ./docs      # 把刚编译的 docs/ 内容发布出去
          publish_branch: main     # 推到发布仓库的 main 分支

四步很简单，但每一行都有讲究：

  • submodules: true：主题 hugo-ivy 是 git submodule。默认 checkout 不带子模块，不写这行构建会直接报「找不到主题」。
  • peaceiris/actions-hugo@v2：一个把 Hugo 装进 runner 的 action。只装二进制，很快。hugo-version: 'latest' 意味着站点一直跟随最新版编译。
  • hugo --minify：压缩产物（去空白、精简 HTML）。publishDir 在 config.yaml 里是 docs，所以产物自然落在 ./docs。
  • peaceiris/actions-gh-pages@v3：把 publish_dir 指向的文件夹内容推送到另一个仓库的分支。publish_branch: main 会整分支覆盖式更新——发布仓库的 main 永远等于「最新一次构建产物」。

跨仓库推送的秘密

这里有个不能绕过的点：workflow 默认拿到的 GITHUB_TOKEN 只在当前仓库内部有效，没法往 mozaitii.github.io 这个「别的仓库」里推。所以要显式给一个 PAT（Personal Access Token）。

配置流程：

  1. 在 GitHub 右上角头像 → Settings → Developer settings → Personal access tokens → Tokens (classic)，点 Generate new token。
  2. scope 勾选 repo（包含读写该账号下所有仓库的权限）。更稳妥的做法是用 Fine-grained token：只授权发布仓库 mozaitii.github.io，权限只给 Contents: Read and write——这样就算 token 泄露也推不了别的仓库。
  3. 回到源码仓库 → Settings → Secrets and variables → Actions → New repository secret，名字填 GH_PAT（和 workflow 里 secrets.GH_PAT 对应），值粘贴 token。

之后 workflow 运行时，${{ secrets.GH_PAT }} 会以密文形式注入。这个值只在服务端存在，不会出现在日志里。

GitHub Pages 配置

发布仓库创建好之后，进 mozaitii.github.io → Settings → Pages：

  • Build and deployment → Source 选 Deploy from a branch
  • Branch 选 main，目录选 / (root)

因为仓库名是 username.github.io 这种用户站点格式，Pages 默认就给它分配 https://mozaitii.github.io/ 域名，无需手动绑定。config.yaml 里的 baseurl 也写死成这个域名，保证站点内的绝对链接指向正确。

一个容易踩的坑：用户站点要求仓库名和 GitHub 用户名完全一致。比如 mozaitii 这个账号，仓库必须叫 mozaitii.github.io，否则 Pages 不会以默认域名发布。

本地到线上

日常写博客，只需要走本地流程：

hugo server -D   # 本地预览（含草稿）
# ……改完内容后
hugo             # 可选：本地看一眼最终产物（输出到 docs/）
git add .
git commit
git push origin main    # ← 到这里就结束了

push 之后，GitHub Actions 在云端重新构建并发布，几分钟内 https://mozaitii.github.io/ 就是最新版。

另外还给仓库配了一个 pre-commit 钩子（.githooks/），提交前自动把待提交的大图压到 1600px。这条流水线和图片压缩是两条独立的链路：压缩管的是「源码怎么进仓库」，部署管的是「源码怎么变成线上站」，互不干扰。

小结

本地写博客，push后自动部署，又有了重新更新博的动力 🚣‍♀️。
