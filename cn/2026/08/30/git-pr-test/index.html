GitHub Pull Request 实践

在团队开发中，通常不会直接在 main 分支上进行功能开发，而是基于 main 创建功能分支，完成开发后将分支推送到 GitHub，通过 Pull Request（PR）进行代码审查，最后合并到 main。

一个典型的 GitHub 协作流程如下：

main
  │
  ├── 创建 feature 分支
  │
  ↓
feature/login
  │
  ├── 开发
  ├── git add
  ├── git commit
  └── git push
          │
          ↓
   Pull Request
          │
          ↓
    Code Review
          │
          ↓
        Merge
          │
          ↓
         main

1. Git 的基本工作区域

Git 中代码主要经历以下几个阶段：

工作区
  │ git add
  ↓
暂存区
  │ git commit
  ↓
本地仓库
  │ git push
  ↓
远程仓库

git add 将工作区修改放入暂存区，git commit 将暂存区内容保存到本地仓库，git push 将本地提交上传到远程仓库。

常用命令：

git status
git diff
git add .
git diff --cached
git commit -m "xxx"
git push

如果已经执行 git commit，此时工作区没有新的修改，git diff 没有输出是正常的。查看最近一次提交的修改可以使用：

git show
git show --stat

2. 创建 Feature Branch

团队开发通常不直接修改 main，而是创建功能分支。例如开发登录功能：

git switch -c feature/login

该命令会创建并切换到 feature/login。

查看当前分支：

git branch

例如，其中 * 表示当前所在分支。：

* feature/login
  main

3. 开发并提交代码

在 feature/login 分支上完成代码修改后，可以使用：

git status
git diff

查看当前修改，然后执行：

git add .
git diff --cached
git commit -m "feat: add login feature"

其中 git diff --cached 用于检查已经加入暂存区的内容。

常见的 Commit Message 类型：

feat:     新增功能
fix:      修复问题
refactor: 重构代码
docs:     修改文档
test:     增加或修改测试

4. Push 到 GitHub

第一次推送新分支：

git push -u origin feature/login

其中 origin 通常是远程仓库的默认名称，-u 是 --set-upstream 的缩写，用于建立本地分支和远程分支之间的跟踪关系：

本地 feature/login
        ↕
远程 origin/feature/login

建立跟踪关系后，后续直接执行即可：

git push

5. Pull Request

分支推送到 GitHub 后，可以创建 Pull Request：

feature/login → main

Pull Request 可以理解为：

请求将一个分支的代码修改合并到另一个分支。

PR 不属于 Git 本身，而是 GitHub、GitLab 等代码托管平台提供的协作功能。除了代码合并，还可以进行 Code Review、CI 检查、代码讨论和权限控制。

6. Mergeability 检查

创建 PR 后，GitHub 会检查两个分支是否存在无法自动解决的代码冲突。

如果看到：

Checking for the ability to merge automatically...

表示 GitHub 正在检查当前 PR 是否可以自动合并。

如果显示：

Able to merge

说明 Git 层面不存在无法自动解决的冲突。

需要注意：

Able to merge 只表示代码可以自动合并，并不代表 Code Review 已经通过。

如果两个分支修改了同一部分代码，可能出现：

This branch has conflicts that must be resolved

此时需要先解决冲突，再进行 Merge。

7. Code Review

Code Review 通常发生在 PR 创建之后、Merge 之前。Reviewer 主要检查代码逻辑、潜在 Bug、代码规范、可维护性、性能以及测试等。

GitHub 中常见的 Review 结果：

  • Comment：提出意见，但不明确批准或拒绝。
  • Approve：审核通过，可以进入合并流程。
  • Request changes：存在问题，需要修改后重新 Review。

如果 Reviewer 要求修改代码，开发者直接修改并提交：

git add .
git commit -m "fix: address review comments"
git push

原来的 PR 会自动更新，不需要重新创建 PR。

8. Approve 与 Merge

需要区分 Approve 和 Merge：

操作含义
Comment提出意见
Request changes要求修改
Approve审核通过
Merge真正执行分支合并

因此：

Approve → Reviewer 同意代码
Merge   → 真正将代码合并到目标分支

PR 作者不能 Approve 自己创建的 PR。如果 GitHub 提示：

Pull request authors can't approve their own pull requests.

表示 PR 作者不能给自己的 PR 执行 Approval，并不代表一定不能 Merge。

如果仓库设置了分支保护规则，例如要求至少一个 Approval，则需要其他开发人员进行 Review。

9. Branch Protection

团队项目通常会对 main 设置保护规则，例如：

  • 必须通过 Pull Request 才能合并
  • 必须至少一个 Reviewer Approve
  • CI 检查必须通过
  • 必须解决所有 Review 对话
  • 禁止直接 Push 到 main

这样可以避免未经审核的代码直接进入主分支。

10. Merge Pull Request

Review 和 CI 检查通过后，可以将 Feature Branch 合并到 main。

GitHub 中通常点击：

Merge pull request

然后确认 Merge。

常见的 Merge 方式包括：

  • Merge commit
  • Squash and merge
  • Rebase and merge

具体使用哪一种，可以根据项目的 Git 工作流决定。

11. 更新本地 main

PR 在 GitHub 上 Merge 后，本地 main 不会自动更新，需要同步远程仓库：

git switch main
git pull

这样本地 main 就会获得 GitHub 上最新的代码。

12. 删除 Feature Branch

功能开发完成并 Merge 后，Feature Branch 通常就可以删除。

删除本地分支：

git branch -d feature/login

如果 Git 检测到分支还有未合并的提交，会阻止删除。确认不需要这些提交后，可以强制删除：

git branch -D feature/login

删除远程分支：

git push origin --delete feature/login

GitHub 在 PR Merge 后通常也会提供 Delete branch 按钮，可以直接删除远程分支。

13. 总结

一个完整的 GitHub PR 工作流可以总结为：

main
  │
  ├── 创建 feature 分支
  │
  ↓
feature/login
  │
  ├── 开发
  ├── git add
  ├── git commit
  └── git push
          │
          ↓
   Pull Request
          │
          ↓
    Code Review
          │
          ├── Request changes
          │       ↓
          │     修改代码
          │       ↓
          │     commit
          │       ↓
          │      push
          │
          ↓
       Approve
          │
          ↓
        Merge
          │
          ↓
         main
          │
          ↓
       git pull
          │
          ↓
     删除 feature 分支

对于个人项目，可以直接使用 git merge 完成分支合并；多人协作项目则更推荐采用：

Feature Branch → Pull Request → Code Review → CI → Merge

这样可以在代码进入 main 之前完成审核、测试和讨论，提高代码质量并方便团队协作。
