博客图片压缩

Mozaitii / 2026-08-02

写动态配图时放了 10 张手机原图，加起来近 24MB。虽然图片设了懒加载，但一滚动就会全量加载，页面明显变慢。这篇记录一下给博客搭的图片压缩方案——现在已经是全自动的了。

先澄清一个误区

一开始我以为 Hugo 编译会自动压缩图片，查了之后发现不会：static/ 目录下的文件是原样拷贝到发布目录的，一个字节都不动。Hugo 确实有图片处理能力（.Resize、.Fit 等），但只对走资源管线的图片生效——需要图片是 page bundle 资源，并且模板里显式调用处理函数。所以要么手动压缩，要么把图片变成「资源」交给 Hugo 处理。我两个都要了。

现在的方案：两层自动压缩

第一层：提交前，git 钩子自动压缩

写了压缩脚本 tools/compress_images.py（基于 Pillow），再配一个 git pre-commit 钩子（.githooks/pre-commit）。每次 git commit 时自动触发：

  • 找出暂存区里 content/ 下的图片，最长边 >1600px 的自动压到 1600px
  • 转渐进式 JPEG、质量 82，顺带去掉 EXIF（更小也更利于隐私）
  • 压缩后反而变大则保留原图
  • 原图先备份到 raw/_originals/（已 .gitignore，不入库，只备份一次）
  • 幂等：已达标的图不动；且永不阻塞提交（Pillow 缺失等只提示放行）

这一步管的是仓库体积和灯箱加载量——入库的图统一不超过 1600px。

第二层：构建时，Hugo 生成 WebP 缩略图

动态（moments）改成 page bundle 模式：每篇动态是一个文件夹，照片放同目录，frontmatter 用 pictures 列文件名。模板里对每张图显式调 .Resize：

{{ $thumb := $res.Resize "480x webp q80" }}   {{/* 网格缩略图 */}}

于是网格里显示的是 480px 的 WebP（每张 12–40KB），而不是一两百 KB 的原图；点开灯箱才加载 ≤1600px 的原图。这一步管的是页面加载量。

模板是双模式的：能解析成 bundle 资源的走 WebP 缩略图，旧文章里 /images/... 绝对路径的原样渲染，兼容不变。

日常流程

# 1. 照片丢进动态的 bundle 文件夹
#    content/moments/2026-08-02-xxx/
#      index.md
#      pic1.jpg
#      pic2.jpg

# 2. frontmatter 里列出文件名（顺序即显示顺序）
#    pictures: ["pic1.jpg", "pic2.jpg"]

# 3. 提交，钩子自动压缩
git add .
git commit        # ← .githooks/pre-commit 自动压到 1600px

新克隆仓库需要做的配置

钩子是通过 git 的 core.hooksPath 指向仓库内的 .githooks/ 目录来启用的。但 core.hooksPath 属于本地仓库配置，不会随克隆带过来——所以每次新克隆或换机器，都要跑这两条命令：

# 1. 启用钩子目录（指向仓库里已提交的 .githooks/pre-commit）
git config core.hooksPath .githooks

# 2. 安装 Pillow（压缩脚本的依赖）
pip3 install Pillow

验证是否生效：

git config core.hooksPath   # 应输出 .githooks

之后正常 git commit 即可，钩子会自动压缩暂存区里的大图。如果没做第 1 步，提交也不会报错——只是图片不会被自动压缩（大图会原样进仓库）。

实际效果

把周末那 10 张手机原图过了一遍新流程：

环节压缩前压缩后
入库（钩子压到 1600px）24.0MB1.9MB（省 92%）
网格缩略图（Hugo 480px WebP）~200KB/张12–40KB/张
灯箱原图（点开才加载）—~100–440KB

网页上 1600px 宽、一两百 KB 的图已经很清晰，手机上看绰绰有余；网格里滚动加载的是十几 KB 的 WebP，快了一个数量级。原图全部在 raw/_originals/ 里留着，随时可取。

一点感受

第一次写这篇时靠的是「意志力」——记得每次手动跑一遍压缩脚本。这次升级成两层自动挡：提交时钩子压缩入库，构建时 Hugo 压缩略图。发图只做一件事——把照片丢进文件夹、写个文件名，剩下的交给工具链。

省下来的流量和加载时间，会让博客一直保持轻盈；而省下来的「记得要压缩」的注意力，是更好的收获。
